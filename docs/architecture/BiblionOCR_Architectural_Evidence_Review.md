# BiblionOCR Architectural Evidence Review

## Purpose

This document preserves the latest architectural review of the BiblionOCR repository and is intended to be given to another AI assistant for cross-checking against the current repository.

The goal is **not** to rewrite the architecture prematurely. The goal is to distinguish what is actually implemented, what is documented, what is emerging, what is planned, what is historical, and what is contradictory.

---

## 1. Current Architectural Picture

The recent evidence suggests that BiblionOCR is evolving toward a layered architecture with these distinctions:

- **System** — the full BiblionOCR platform.
- **Workspace** — the development tree of the System.
- **Project** — an externally stored user work unit generated by the System.
- **Workflow** — an ordered business-level path toward an outcome.
- **Process** — a concrete executable operation within a Workflow.
- **Stage** — a named state boundary within a Workflow or Process chain.
- **Module** — a concrete application or code unit exposing capabilities.
- **UI Surface** — a user-facing interaction layer.
- **Artifact** — a durable file or folder produced, consumed, or transformed.
- **Reference Data** — shared reusable data that supports runtime behavior.
- **Session** — persisted runtime context used to restore operator/module state.
- **Event** — an immutable record of a meaningful system transition.

The Design Specification explicitly establishes these distinctions and says that its purpose is to provide common vocabulary for architecture, UI behavior, project generation, and future module work.

---

## 2. Project vs. Workspace

The Design Specification makes this distinction explicit:

- **Project:** user work product under the external Projects root.
- **Workspace:** development tree of the application itself.

The important architectural implication is:

> The System generates Projects but is not itself a Project.

This appears to be a deliberate evolution beyond treating repository-resident `Model/Project` material simply as the user's project.

Project generation should therefore be curated rather than a broad copy of the development Workspace.

---

## 3. MyServer Ownership

The current repository evidence strongly supports:

> **Project administration is centralized in MyServer.**

The repository describes New Project and Project Settings as MyServer responsibilities, and the Workflow Wizard documentation reinforces that project workflow administration remains anchored in MyServer.

Current conceptual boundary:

- **MyLauncher** — landing/help/dashboard and workflow entry surface.
- **MyServer** — project administration and workflow control.
- **Individual modules** — module/page-level work.

This should be treated as a strong architectural conclusion unless current source contradicts it.

## 4. Workflow / Process / Stage

The Design Specification defines:

- Workflow = larger business-level sequence.
- Process = executable transformation within a Workflow.
- Stage = named state boundary.

Current workflow implementation appears to reflect this model.

The Workflow Wizard uses staged paths such as:

`0-MainUI → 1-PreProcess → 2-TrainTesseract → 3-Process → 4-PostProcess`

This suggests the architecture is not merely theoretical: workflow/stage concepts are appearing in actual implementation and documentation.

Potential relationship:

```text
Workflow
   ↓
Stages
   ↓
Processes
   ↓

```

This relationship should be verified against current source before being declared normative.

## 5. Project Creation Architecture

The supplied v2.0 architecture document describes an event-sourced project creation system:

```text
UI
 ↓
MyServer controller
 ↓
ProjectCreationEngine
 ↓
EventBus
 ↓
SQLiteEventStore
```

It specifies:

- ProjectCreationEngine in `Core/engine.py`
- lifecycle states:
  `INIT → VALIDATE → PROVENANCE → RIS → WRITE → COMPLETE / FAILED`
- EventBus as an in-memory event dispatcher
- SQLiteEventStore as an append-only event log
- RIS generator producing an immutable, hash-stamped provenance record
- MyServer as dependency-injection/wiring only
- Engine independent of UI
- EventBus not mutating state

### Important caution

The repository contains Core components whose names correspond closely to this architecture, including:

- `engine.py`
- `event_bus.py`
- `event_store.py`
- `ris.py`
- `state.py`
- `project_database.py`
- `project_tracking.py`
- `workflow_wizard_actions.py`

However, **filename correspondence does not establish implementation semantics**.

The exact claims of the v2.0 document—especially that state is derived from events and that SQLite is an append-only authoritative event store—must be verified against current source before being treated as implemented facts.

---

## 6. SQLite

SQLite project persistence is definitely present in the current repository architecture.

Generated Projects are described as receiving files such as:

- `Model/Project/Data/sqlite/project_metadata.sqlite`
- `Model/Project/Data/sqlite/Project Settings.db`

The Workflow Wizard also uses project metadata persistence.

However, this does **not by itself prove** that the SQLite event store described in the v2.0 architecture is currently the authoritative source of system state.

That distinction requires source verification.

---

## 7. RIS

RIS/provenance is clearly an active project-creation concern.

Recent repository history includes work involving:

- restoring editable RIS fields during provenance loading,
- exposing RIS specification fields for editing,
- project wizard source/provenance behavior.

The Design Specification identifies `project.ris.json` as a Project artifact.

Thus:

```text
Project Creation
      ↓
Provenance
      ↓
RIS Artifact
      ↓
Generated Project
```

appears strongly supported.

The exact implementation of locking, hashing, and event-log duplication still requires verification.

## 14. Important Principle

Do not silently reconcile conflicting documents.

Do not infer implementation from filenames.

Use the repository source and commit history as evidence, and explicitly label inference as inference.

The architecture should be documented from evidence rather than imposed by assumption.
